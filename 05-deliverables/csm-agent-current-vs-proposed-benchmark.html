Current agent and proposed design

A short comparison of the problems seen today, the proposed fix, and the evidence available now.

Evidence period: 24 to 31 August 2026 Databricks access was read-only No Databricks object was changed

What we know

Confirmed Current problems

Saved results show repeated-TEU sums, invalid SQL, incorrect percentage scaling and answers that continued after a query failed.

Local check Proposed foundation

The 100-row preview produced six agent views. Five applicable data checks passed. Three swap checks were blocked by missing operational identifiers and date coverage.

Not tested Production result

The normalized views have not been deployed and tested by the agent. There is no measured production accuracy, latency or reliability improvement yet.

Simple conclusion. Keep the proposed design because it removes known sources of agent error. Do not claim it is faster or more accurate until the same questions are run against both agents.

How the SQL becomes simpler

Example 1: customers with the highest rejection risk

Question: Which customers have the highest rejection risk?

Observed Before hardening

Shortened from the captured query without changing the calculation problem.

SELECT
  customer,
  sales_rep,
  SUM(reviewed_teu) AS reviewed_teu,
  SUM(rejected_teu) AS rejected_teu,
  SUM(booked_teu) AS booked_teu,
  ROUND(AVG(rejection_rate) * 100, 1)
    AS rejection_rate_pct
FROM dev.sales_ai_assistant_gold.csm_csal_summary
WHERE rejected_teu > 0
GROUP BY customer, sales_rep
ORDER BY rejected_teu DESC;
Problem: It sums repeated booking values and multiplies an already stored percentage by 100.

Proposed One approved view

The view already contains the metric at the correct level.

SELECT
  customer_name,
  agreement_id,
  service_code,
  sail_week,
  rejection_rate_pct,
  rejected_teu,
  days_to_cutoff
FROM dev.sales_ai_assistant_gold.agent_booking_risk_current
WHERE is_high_rejection = TRUE
ORDER BY rejection_rate_pct DESC, rejected_teu DESC
LIMIT 50;
Change: The agent filters and sorts. It does not rebuild the percentage.

Example 2: customers with low fulfillment

Question: Show customers with low fulfillment percentage.

Today the agent can choose different formulas or the old hard-coded flag. The proposed query uses one approved risk band:

SELECT
  customer_name,
  agreement_id,
  service_code,
  sail_week,
  booking_fulfillment_pct,
  fulfillment_risk_band
FROM dev.sales_ai_assistant_gold.agent_booking_risk_current
WHERE fulfillment_risk_band IN ('HIGH', 'CRITICAL')
ORDER BY booking_fulfillment_pct, customer_name
LIMIT 50;

The risk band must be calibrated from an agreed historical period and approved before production use.

One test is needed to finish the comparison

  1. Ask the same 15 approved questions to the current agent and the normalized agent.
  2. Repeat every question three times in a clean conversation. This is 90 agent runs.
  3. Record whether the answer is correct, total response time, failures and generated SQL.
  4. Report correct-answer rate, p50 and p95 response time, completion rate and whether repeated runs return the same rows.
Why those numbers are not shown. The normalized views are not deployed, and this session has read-only VM access. Real before-and-after results require an authorized run.
